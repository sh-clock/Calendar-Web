## Findings, with evidence

### VP6-F1 (Low) — `boot-guard.js` not syntax-checked in CI
`.github/workflows/ci.yml:40-46` runs `node --check` on `js/app.js`, `js/api.js`, `js/crypto.js`, `js/ical.js`, `js/calendar-core.js` — **`js/boot-guard.js` is absent from the list**, yet it is the first script the live page loads (`index.html:26`, blocking `<head>` script carrying the sec-S5-F3 frame-buster). It is covered by the hex-guard scope (`js/` is in the `git grep` path list) and by the Pages copy glob (`js/*.js`), but no CI step parses it. Verified it currently passes: `node --check js/boot-guard.js` → OK (run locally during this audit). Fix: add one line to the syntax step.

### VP6-F2 (Medium, latent) — `.secrets/` not git-ignored
`scripts/lib-prod-material.mjs:7-22` resolves credentials in order: (1) `CALENDAR_SECRETS` env, (2) `/home/z/my-project/.secrets/credentials.json`, (3) **`<repo>/.secrets/credentials.json`**. `.gitignore` covers `.dev.vars`, `.dev.vars.*`, `.env`, `secrets*.json`, `node_modules/`, `.wrangler/` — but **not `.secrets/`**: `git check-ignore -v .secrets/foo` → "NOT ignored", and `credentials.json` matches no existing pattern (`secrets*.json` requires the `secrets` prefix). The repo is public (per the CI hex-guard's own comment). A future contributor following the code comment and using the repo-local layout would commit live key material with `git add -A`. **Zero current exposure**: no `.secrets/` directory exists in the repo; the operator's real layout is outside it (`/home/z/my-project/.secrets/`, confirmed present, untracked). Fix: add `.secrets/` to `.gitignore` (and/or drop the repo-local fallback from `lib-prod-material.mjs`).

### VP6-F3 (Low) — S3 agent unaccounted for
`WORKLOG.MD:2580-2582`: "The crashed session's **8-agent** security pentest (S1 network/edge, S2 auth, S4 concurrency, S5 client, S6 zero-knowledge invariant, S7 crypto, S8 protocol conformance)" — that enumeration lists **7** scopes. `audit-d/` contains `sec-S{1,2,4,5,6,7,8}-findings.md` — **no `sec-S3-findings.md`**, and a worktree-wide `rg "sec-S3"` returns zero references. Either the "8-agent" count is wrong or the S3 agent's output was lost in the crash; unexplained either way. No security impact inferred (all listed findings were dispositioned), but the coordination artifact should state what S3 was and where its output went.

### VP6-F4 (Info) — out-of-repo secret file permissions

### VP6-F5 (Info) — `*SCRUBBED*` remnants in reachable history are placeholders, not leaks
Python scan over all 54 reachable commits / 372 distinct blobs found the string `SCRUBBED` in: 11 script files at `8aba3ad32` (`scripts/{check-seed,debug-prod-render,decrypt-prod,drag-debug,e2e-prod,measure-month,measure-week-local,measure-week,repro-user-flow,reseed-prod,seed-prod}.mjs`) and `test/crypto-parity.mjs` at `c2654d9`/`c26a97684`. Verified content: `kDataHex: '*SCRUBBED*<='` style placeholders — these are the S7-F1 strippings. `grep -cE '[0-9a-f]{64}'` over each of those historical script blobs → **0**. The only hex64 in historical `test/crypto-parity.mjs` (lines 56/57/70 at `8aba3ad32` and `c2654d9`) are `aes1Hex` (the canonical public test key `000102…1f`), `wrappedHex` and `rowCtHex` (deterministic functions of public inputs) — and the three sensitive-looking HKDF literals (`kDataHex`/`authUiHex`/`authClockHex`) were scrubbed in those revisions, restored only at HEAD (`54c2fca`) after a regeneration proof. **Independently re-proved during this audit:** `python3 scripts/gen-kat.py` (pure public constants: `kat-password-0123456789`, salt `0011..ff`, `AES1 = bytes(range(32))`, nonce `0102..0c`) reproduces all three restored literals byte-exactly → they are not deployment secrets.
